# 教务系统协议实测事实

## 协议分析（实测）

以下结论全部来自对 `jwgl.hutb.edu.cn` 的实际抓取与代码逆解，不是推测。

### 1.1 整体架构

```
App
 ├─ WebView → CAS 统一身份认证 (cas.hutb.edu.cn/lyuapServer)
 │             └─ 登录成功后下发 jwgl 域的 JSESSIONID
 └─ OkHttp  → 强智 jsxsd (jwgl.hutb.edu.cn/jsxsd)
               └─ 携带 JSESSIONID 查课表
```

* **教务系统厂商**：强智科技（jsxsd）
* **入口**：`http://jwgl.hutb.edu.cn/` → 302 跳转统一身份认证
* **统一认证**：凌育平台 `https://cas.hutb.edu.cn/lyuapServer/login?service=...`
* **公网可达**：是（`218.76.42.103`），无需校园网 VPN

### 1.2 登录链路

#### 路径 A：统一身份认证（学生实际走的路径）

`http://jwgl.hutb.edu.cn/` 的响应体是一段跳转脚本：

```javascript
window.location.href = 'https://cas.hutb.edu.cn/lyuapServer/login?service=http%3A%2F%2Fjwgl.hutb.edu.cn%2F'
```

CAS 是 React SPA，登录接口为：

```
POST https://cas.hutb.edu.cn/lyuapServer/v1/tickets
Content-Type: application/x-www-form-urlencoded

username=<学号>&password=<RSA 密文>&service=<回跳地址>&loginType=false&id=<验证码id>&code=
```

* `password`：用 CAS 页面内置的 RSA 公钥（`public_exponent=010001` + 1024 位 modulus）加密
* **验证码**：TAC 滑块验证码
  * `GET /lyuapServer/kaptcha?uid=<uid>` 获取滑块
  * `POST /lyuapServer/validateKaptcha` 校验，通过后返回 `id` 填入登录请求
* 返回 `data.code` 常见取值：`CODEFALSE`（验证码错）、`NOUSER`（账号密码错）、
  `ISMODIFYPASS`（首次登录改密）、`NETWORKCOMMITMENT`（需要补充信息）

#### 路径 B：jsxsd 本地登录页（教师 / 老账号）

`http://jwgl.hutb.edu.cn/jsxsd/` 返回的登录页中，`submitForm1()` 的逻辑是：

```javascript
var account = encodeInp(xh);                        // 自定义 Base64（等价标准 Base64）
var passwd = encodeInp(pwd);
var plantext = account + "%%%" + passwd + "%%%" + (new Date().getTime());
var rsaEnc = new JSEncrypt();
rsaEnc.setPublicKey(RSA_PUBLIC_KEY);                // 1024 位 X.509 公钥
var encoded = rsaEnc.encrypt(plantext);             // RSA/ECB/PKCS1Padding → Base64
document.getElementById("Form1").submit();           // POST /jsxsd/xk/LoginToXk
```

提交前会先 `POST /jsxsd/xk/LoginToXk` 探测账号类型：

```
POST /jsxsd/xk/LoginToXk
xh=<学号>&zhjc=1
→ 返回 JSON 数组，如 ["1"]
```

返回 `["0"]` 表示"学生登录请通过统一身份认证地址"（即必须走 CAS）；
返回 `["1"]` 才会走本地的 RSA 加密表单流程。

**验证请求前还会带上 4 位图形验证码**：`GET /jsxsd/verifycode.servlet`（JPEG），
输入框 `randomCode`。

### 1.3 需要哪些凭据

| 凭据 | 必需性 | 说明 |
|---|---|---|
| 学号 | 必需 | CAS 用户名 |
| 密码 | 必需 | 明文提交给 CAS，App 不保存 |
| 图形验证码 | jsxsd 路径需要 | 4 位图片码；CAS 路径改为滑块 |
| 滑块验证 | CAS 路径需要 | 需真人拖动，无法纯 HTTP 绕过 |
| 身份证/手机号 | 仅忘记密码时 | 走 CAS 的 `/lyuapServer/custom/...` |

### 1.4 加密与会话保持

**加密**（两处，均为 RSA + Base64）：

| 环节 | 算法 | 备注 |
|---|---|---|
| `encodeInp()` | 标准 Base64 | conwork.js 混淆后与标准 Base64 等价 |
| jsxsd 密码 | RSA-1024, `RSA/ECB/PKCS1Padding` | 明文 `base64(账号)%%%base64(密码)%%%时间戳` |
| CAS 密码 | RSA-1024 | modulus/public_exponent 内置在 CAS 的 JS bundle |

Java 侧用 `Cipher.getInstance("RSA/ECB/PKCS1Padding")` 即可完全对齐（已用 OpenSSL 交叉验证）。

**会话保持**：

| Cookie | 域 | 作用 |
|---|---|---|
| `JSESSIONID` | jwgl.hutb.edu.cn | 强智主会话，HttpOnly |
| `SERVERID` | jwgl.hutb.edu.cn | 负载均衡节点标识 |
| `TGC` / `CASTGC` | cas.hutb.edu.cn | CAS 票据，不落盘 |

会话失效的判别特征（实测文本）：

* `"用户没有登录，请重新登录！"` — `app.do` 接口
* `"请先登录系统"` — jsxsd 页面
* `"该帐号不存在或密码错误"` — CAS 侧

#### 教室（教学安排）查询

改版后的"全校性教室课表"页由**查询页 + 结果 iframe** 两部分组成：

```
# 查询页（拿表单与下拉框）
GET  http://jwgl.hutb.edu.cn/jsxsd/kbcx/kbxx_classroom?xnxqh=<学期>&xqid=<校区>

# 结果页（表格）
POST http://jwgl.hutb.edu.cn/jsxsd/kbcx/kbxx_classroom_ifr
Referer: http://jwgl.hutb.edu.cn/jsxsd/kbcx/kbxx_classroom
Content-Type: application/x-www-form-urlencoded

xnxqh=<学期>&jzwid=<教学楼>&xqid=<校区>&zc1=<起周>&zc2=<止周>
```

**实测确认的三条硬规则**（都在真机上验证过）：

| 规则 | 原因 |
|---|---|
| **不要提交 `classroomID`** | 服务端只认教室的内部编码，而该编码只能由并不存在的 `class_query` 接口给出。提交教室名会得到一张 4.6 KB 的空表 |
| **`jzwid` 单独就能定位教学楼** | 实测 `jzwid=00002`（日新楼）稳定返回该楼 31 间教室、`jzwid=00001`（至诚楼）返回 57 间、`jzwid=00003`（乐知楼）49 间，**不会混入别的楼** |
| **`xqid` 与 `jzwid` 可以同时提交** | 2026-10-23 复测：两种提交方式返回的**字节完全一致**（日新楼 178 971 B、立德楼 142 206 B……），服务端在有 `jzwid` 时会忽略 `xqid`。与校方网页表单一致，两个都带即可 |

> 早前记录的"同时提交会返回 4 / 17 / 43 / 57 个教室"是**服务端高负载时的截断**，
> 与参数组合无关：同一个请求重复多次也会不一致。空/半张表会表现为「教室数忽多忽少」，
> 真正的定位方式是看**响应里有没有 `kbtable` 的数据行**。


> 另一个坑：**`/jsxsd/kbxx/class_query` 与 `/jsxsd/view/kbxx/jx0601_select.jsp` 在本校部署里根本不存在**。
> 服务端对不存在的路径返回一张 762 字节的「提示：非法访问！」页面，
> 与真实存在但被拒绝的接口**完全一样**（实测：随便编一个 `/jsxsd/kbxx/nonexistent_xyz` 返回同样的 762 字节）。
> 这两个路径恰恰是教务系统自己的页面脚本里引用的 —— 也就是说**学校官网的教室下拉框同样是坏的**，
> 不能指望从它那里拿到教室清单。

##### 查询页的下拉框（实测）

| 字段 | 含义 | 取值示例 |
|---|---|---|
| `xnxqh` | 学年学期 | `2026-2027-1` |
| `skyx` | 上课学院（系） | `00001`=[01]经济与贸易学院 |
| `xqid` | **校区** | `0t`=月亮岛校区、`00001`=南校区、`00002`=北校区 |
| `jzwid` | 教学楼 | 由 AJAX 加载，静态页里只有「请选择」 |
| `classroomID` | 教室 | **永远是空的** —— 加载它的 `class_query` 接口不存在 |
| `zc1` / `zc2` | 周次起止 | `1`…`30` |
| `jc1` / `jc2` | 节次起止 | 留空表示全部节次 |

##### 教学楼 / 教室的级联加载

教学楼与教室**不是服务端渲染的**，而是页面脚本按上级选择动态填充：

```
GET|POST http://jwgl.hutb.edu.cn/jsxsd/kbcx/getJxlByAjax
        ?xqid=<校区>&jzwid=<教学楼>&xnxqh=<学期>
→ [{"dm":"6F57A89B0A67435AB9E528529A6F2840","dmmc":"风华楼"}, …]
```

**实测（2026-10-23 真机）**：

* 返回字段是 `dm`（场地代码）与 `dmmc`（场地名称）；
* **`xqid` 是生效的**：`xqid=0t`（月亮岛校区）返回 3 个教学楼，
  `xqid=00001`（南校区）返回 13 个，不带参数返回全校 22 个；
* `jzwid` 只在「查该教学楼的教室」时才有意义，而教室恰恰查不到（见下）。

各版本字段名不一，App 的 `parseAjaxOptions` 分三层取名：
先按候选键名（`DM/dm/id/value/code/jzid/jzwhid` 与 `MC/mc/dmmc/name/text/label/jzmc/jzwh/…`）匹配，
再**取任意一个含中文的字段值**（教学楼名称必为中文，这一层兜住所有没见过的键名），
最后只在编码可读时用它兜底；哈希形式的编码直接丢弃，不再猜测。

> **实测坑**：教学楼的场地 ID 有时是 32 位十六进制串（`6F57A89B0A67435AB9E528529A6F2840`），
> 直接当名称展示就是"乱码"。因此：
> - 解析时判定哈希形态的值为系统内部码，不采纳为显示名（`isOpaqueRoomName`）；
> - 若名称最终仍缺失，用该楼教室名反推（`风华楼302` → `风华楼`，`deriveBuildingName`）；
> - 教室条目在名称与编码相同时只显示一次，编码是哈希时不展示。

##### 教室清单的唯一可行来源：课表表格首列

既然没有教室接口，教室清单就**从教室课表结果页反推**：
结果表格的**行首单元格就是教室名**（如「至诚楼A101*(智慧)」「立德楼A602」），
一行 = 一个教室。`JsxsdScheduleParser.parseRoomLabels(html)` 取出这些名字，
`JsxsdApi.fetchClassrooms()` 把它们同时当作编码与显示名。

> **为什么这比 AJAX 更可靠**：教室课表本来就是按「某教学楼 × 某周」生成的，
> 首列列出的就是该楼该周**实际有课的教室**，比全校教室字典更贴合查询意图。

##### App 的降级策略

1. 教学楼：先读页面上的 `#jzwid`（若服务端已渲染）→ 再 POST 查询页让服务端填表
   → 最后用 `getJxlByAjax` 按校区逐组参数试（GET/POST 各试一次）
2. 教室：**没有降级路径**，直接由课表表格首列反推
3. 具体到某间教室时，**不提交 `classroomID`**，改为在客户端按教室名过滤整栋楼的课表

##### 教室课表结果页很慢，必须加超时与缓存

实测这台服务器生成教室课表**很慢**，且高负载时**会中途截断**响应（拿到半张表）：

| 场景（2026-10-23 晚复测） | 响应体积 | 耗时 | 教室数 |
|---|---|---|---|
| `jzwid`（至诚楼） | 322 816 B | 3.8 s | 57 |
| `jzwid`（日新楼） | 178 971 B | 2.2 s | 31 |
| `jzwid`（立德楼，月亮岛） | 142 206 B | 1.1 s | 22 |
| 仅 `xqid`（南校区） | 1 067 818 B | 12.9 s | 192 |
| 不带参数（全校） | 1 946 542 B | 19.6 s | 350 |
| 非教室类场馆（体育馆 / 图书馆 / 食堂） | 4 558 B | 0.1 s | 0（空表，表头仍在） |

服务端生成越大的表越慢、越容易截断。因此 App 做了三件事：

1. **读超时单独放宽到 90 秒**（`EduHttpClient.postFormWithTimeout` 的 `readTimeoutSeconds`，
   默认值仍是 30 秒，其他接口不受影响）；
2. **结果页缓存**（`JsxsdApi.roomTableCache`，LRU，淘汰阈值 3 份，键为
   `学期|周次|校区|教学楼`）。
   教室清单与课表内容来自**同一个页面**，没必要为"选教学楼"和"查课表"各拉一次；
   缓存命中时日志会打印「教室课表页命中缓存：…」，也顺带避免了重复的 300 KB 请求；
3. **没选校区/教学楼时不去查**。此时服务端会把全校 350 间教室都返回来（1.9 MB / 20 s），
   App 直接等用户选好教学楼再发请求。


#### JSON API（备用路径）

强智自带 `/app.do` 接口族，部分部署开放：

```
POST http://jwgl.hutb.edu.cn/app.do
method=authUser&xh=<学号>&pwd=<密码>        → 返回 token
POST http://jwgl.hutb.edu.cn/app.do
method=getKbcxAzc&xh=<学号>&xnxqid=<学期>&zc=<周次>
```

`getKbcxAzc` 返回字段：

| 字段 | 含义 |
|---|---|
| `kcmc` | 课程名称 |
| `jsxm` | 教师姓名 |
| `jsmc` | 上课教室 |
| `kssj` / `jssj` | 上课/下课时间 |
| `kcsj` | 上课时间，格式 `x0a0b`（星期 x 的第 a、b 节） |
| `kkzc` | 开课周次 |
| `sjbz` | 单双周标记 |

> **本机实测**：`jwgl.hutb.edu.cn/app.do` 存在，但当前状态下所有 method（含 `authUser`）
> 均返回"用户没有登录，请重新登录！"。因此 App 以 **HTML 解析为主路径**，
> 仅 `getXnxq` 作为学期列表的优先尝试路径（`fetchSemestersViaAppApi`），
> 课表查询不走 JSON API。

其他可用 method（来自强智通用文档）：`getXqcx`（校区）、`getJxlcx`（教学楼）、
`getKxJscx`（空教室）、`getCurrentTime`（当前周次）、`getXnxq`（学年学期）。

### 1.6 解析策略

`JsxsdScheduleParser` 的三层宽松解析：

1. **表格定位**：`table#kbtable` → `#kbtable_show` → `[id*=kb]` → `[class*=kb]` → 首个 table。
   只按已知选择器命中；全部落空即抛解析错误，不做"取行数最多的表"之类的猜测
2. **星期列推断**：表头必须精确识别出至少两个互不相同的星期
   （`星期一`/`周一`/`礼拜一`/`Mon` 等；单元格只做精确匹配，
   课程名里的「高等数学(一)」「日语」不会被当成星期）。
   识别失败时个人课表与教室课表**都直接抛 `HutbError.Parse`**，绝不按列序猜
3. **单元格切分**：`<br>` 与块级标签切行 → 按"名字行"启发式切分多门课 →
   首行定为课程名，其余按语义归位（教师/班级/教室/周次/性质）

课程块切分规则：已收集到教师/班级/教室/周次之一后，再遇到"不像教师/班级/教室/周次/性质"
的行，判定为下一门课的开始。个人课表还要额外处理 `div.kbcontent` 隐藏块，
见下面「个人课表的特殊结构」。

> 已修正的三个坑：
> ① 不能用"2-4 个汉字"判定教师 —— "数据结构"这类课程名会被误判；
> ② 班级名常为"专业代码+班号"（`计科2201`）而非带"班"字，需用
> `[\u4e00-\u9fa5]{2,6}\d{2,4}` 识别；
> ③ 节次数字不能裸取 —— "至诚楼A201"含"20"，必须先做形态校验
> （必须含"节"、或整串就是节次区间/时间）才允许抽数字。

> **还有一个隐蔽的坑：JSoup 的 `prettyPrint` 必须关掉**（`JsxsdHtml.kt`）。
> JSoup 默认开启美化输出，序列化单元格时会把文本节点里的换行**折叠成空格**。
> 强智的教室课表正好把"教师"与"周次"之间的分隔写成了换行
> （`陈小春\r\n(1-8周)`），一旦被折叠成空格，教师名就会和周次粘在一起，
> 教师字段直接解析不出来。

#### 个人课表（`xskb_list.do`）的特殊结构

个人课表和教室课表不是同一套渲染，踩过三个坑：

1. **节次标签在 `<th>` 里**。教室课表用 `<td>`，个人课表用 `<th>`。
   早期按 `select("td")` 取格子会**丢掉行首那个节次格**，
   星期列整体错位一列（星期一的课跑到星期二），星期日永远解析不到。
   现在统一用 `row.select("th, td")` 把两者一起数。
2. **每门课拆成两个 div**：
   `div.kbcontent1` 是可见部分（课程名 / 周次 / 教室 / 班级），
   `div.kbcontent` 是隐藏部分，**多了教师与 `[01-02-03]节` 节次标记**。
   两个 div 指同一门课，只取隐藏的那个，否则一门课会被算成两门，
   还会多出一门叫「[01-02]节」的假课。
3. **节次要信隐藏块里的标记**。行首标签只能给出"第几节**对**"（0102、0304…），
   连堂课横跨多行时并不准；`[01-02-03]节` 里的首尾数字才是真实占用节次。
   同一门课会在多行各出现一次，按「星期+课程+教师+教室+周次+节次」去重即可。

另外 `&nbsp;` 在 JSoup 里会被还原成不换行空格 `U+00A0`，
它既不被 `trim()` 去掉也不匹配 `\s`，"0102节&nbsp;" 因此必须先显式替换。

### 1.6.1 学期列表的多路径获取（改版兼容）

教务系统改版后，"学年学期"下拉框的位置与写法会变，甚至整个消失。
`JsxsdScheduleParser.parseSemesters` 采用**九策略逐级降级**，任意一种命中即返回：

| # | 策略 | 命中条件 |
|---|---|---|
| 1 | 语义化下拉 | `<select>` 的 id/name 含 `xnxq` / `xq` / `semester` / `term` |
| 2 | 任意下拉 | 所有 `<select>` 中 option 文本含"学期"的（ID 形如 `2025-2026-1` 的优先） |
| 3 | 纯 ID 值选项 | option 的 value 本身就是 `2025-2026-1`，即使文案不含"学期"也接受 |
| 4 | 隐藏域 | `<input type="hidden" name="xnxq01id" value="2025-2026-1">` |
| 5 | 链接参数 | `<a href="...?xnxq01id=2025-2026-1">`（改版后按学期分页的链接列表） |
| 6 | 内联 JSON | `{"xnxq01id":"...","xqmc":"..."}` 内嵌在页面脚本里 |
| 7 | 自定义下拉 | `<div data-value="2025-2026-1">` 之类 JS 组件 |
| 8 | 纯文本正则 | 页面出现 `2025-2026学年第一学期` / `2025-2026-1` |
| 9 | 当前学期文案 | 页面出现 `2026-2027学年第一学期  第  7周`（框架页/登录页右下角） |

> **策略 6 的坑**：内联 JSON 里多个对象只隔几十字符，
> 用固定窗口做前后配对会**串位**（A 的 ID 配到 B 的名字）。
> 正确做法是按 **JSON 对象边界**（就近的 `{` … `}`）配对。

`JsxsdApi.fetchSemesters()` 的取数顺序：

1. **JSON API `getXnxq`**（首选）—— 强智自带接口，直接返回结构化 JSON：
   ```json
   [{"xnxq01id":"2026-2027-1","xqmc":"2026-2027学年第一学期"}, ...]
   ```
   比解析 HTML 稳定得多，只需已登录会话。
   方法名按 `getXnxq` → `getXnxqList` → `queryXnxq` → `getXnxqh` → `getXnxxq` 依次尝试。
2. **候选页面轮询**：`xsMain.jsp` → `kszx/cxks` → `framework/main.jsp` →
   `xskb_list.do` → `kszx/xskb.jsp` → `xsIndex.jsp` → `xsTop.jsp` → …
3. **兜底**：从课表查询页反查学期下拉。

### 1.6.2 页面结构指纹（改版排查的核心工具）

教务页面动辄上百 KB，传输和人工阅读成本都很高。
`HtmlStructureProbe` 把页面压缩成一份**结构指纹**，只保留改版排查真正需要的信息：

| 区块 | 内容 | 用途 |
|---|---|---|
| 表单 | action / method / 字段名 | 判断查询参数怎么传 |
| 下拉框 | id / name / 全部选项 | 判断学期、场地怎么选 |
| 表格 | id / class / 行数 / **真实列数** / 表头（含 colspan）/ 样例行 | 判断课表怎么解析 |
| 候选接口 | 链接 href、表单 action、脚本里的 url | 暴露改版后新出现的接口路径 |
| 学期线索 | 页面文本里的"学年/学期"片段、值含学期 ID 的元素 | 定位学期数据的真实位置 |
| 页面脚本 | 含 AJAX 调用的内联脚本片段 | 找出动态加载下拉框的接口路径与参数 |
| 原始响应 | 非 HTML 响应（JSON）的正文 | 拿到 AJAX 返回的真实字段名 |
| 来源 | 快照的 tag / url / time | 判断这份内容是哪个请求返回的 |

指纹是一份 **2~4 KB 的纯文本**，可以直接复制粘贴反馈，
**不需要传输原始 HTML**。

快照文件的头部也会自动写入同一份指纹，
所以即使不打开 App，从文件开头也能看出"这页到底长什么样"。

### 1.6.3 星期 / 节次筛选：为什么放在客户端

课表页加了**星期几**与**第几到第几节课**两组筛选（`ScheduleFilter`）。
实测结论是这两个维度**都必须客户端过滤**：

* 服务端**没有星期参数**。`xq` / `xqid2` / `weekday` / `xqmc` 全部被忽略，
  响应字节完全一致（`probe_jc.py` 实测）。
* 服务端**有**节次参数 `jc1` / `jc2`，但它会**重写表格结构**
  （表头变成 `0102`×7），且一次往返要 1~50 秒。
  为了一次筛选切换去重拉整张表，体验不可接受。

因此两个维度都在客户端做：

* 星期筛选决定**渲染哪几列**（`filter.visibleWeekdays()`）；
* 节次筛选决定**渲染哪几行**（与 `PERIOD_SLOTS` 求交集）；
* 课程命中判定是**区间相交**：`start <= endPeriod && endPeriod >= startPeriod`，
  连堂课只要有一节落在范围内就算命中；
* 节次没解析出来的课程不因节次筛选被误伤（`endPeriod <= 0` 时直接放行）。

筛选状态放在 `TimetableUiState.filter`，两种查询模式共用同一套筛选条。

### 1.7 教室（教学安排）页的特殊处理

教室课表与个人课表的表格结构**不同**，不能共用同一个解析函数：

| | 个人课表 `xskb_list.do` | 教室课表 `kbxx_classroom_ifr` |
|---|---|---|
| 行 | 节次 | 场地（教室） |
| 列 | 星期 | 星期 |
| 教室来源 | 单元格内的文本行 | **行首单元格** |

因此拆成两个解析入口：

* `parseSchedule()` —— 个人课表，行首是"第1-2节"
* `parseRoomSchedule()` —— 教学安排，行首是"至诚楼A201"

`parseRoomSchedule` 额外做了四件事：

1. **rowspan / colspan 网格展开**：强智表头常把"星期一"横跨多个节次列，
   直接 `select("td")` 会列错位。展开时保存**元素**而非文本 ——
   `Element.text()` 会把 `<div>` 内的多行压成一行，导致课程名/教师无法按行切分。
2. **行首语义判定**：先判断行首是"节次"还是"场地"，
   以兼容三种表格形态（场地为行 / 节次为行的同构表 / 双行表头）。
3. **连堂课合并**：服务端把连堂课写进它跨到的**每一个**格子
   （4 连堂 = 0102 与 0304 两格内容完全相同），且**不用 rowspan**。
   直接按格解析会让同一门课在课表上重复出现 2~3 次。
   现在把同行、同一天、相邻且内容相同的格子并成一次课，节次取首格的起始到末格的结束。
4. **按教室名在客户端过滤**：服务端不认教室名（`classroomID` 只收内部编码），
   所以整栋楼的课表先全量解析，再按行首教室名做子串匹配过滤。

   > **过滤不依赖教学楼名**：教学楼「月亮岛立德楼」下的教室名却是「立德楼A401」，
   > 若要求两个名字都匹配就会筛空。因此只要指定了教室，就**只按教室名过滤**；
   > 没指定教室时才退到按教学楼名过滤。
   > 过滤结果为空且原始数据里没有任何教室名时，回退成不过滤，
   > 避免"教室名写错 → 空白课表"。

> **紧凑节次的坑**：列头是 `0102`/`0304` 这种两节合并的写法，
> 拆成第 1-2 节 / 第 3-4 节时，行首的「场地代码」（如 `0301`）形态与节次区间完全一样。
> 不能靠"首位数字 < 末位数字"判断行首是不是节次，否则会把整行教室丢掉。

> **真实表格是 43 列**：1 列教室 + 7 天 × 6 个节次对（`0102`/`0304`/`0506`/`0708`/`0910`/`1112`）。
> 表头是 `<th colspan="6">星期一</th>` × 7。
> 结构指纹里必须标出**真实列数**和表头的 colspan，
> 否则只截前 8 格看样例行，会误以为"星期一第1-2节、星期二第3-4节"这种排列。

> **服务端按 `jzwid` 过滤，但会把同校区的别的场馆顺带带出来**：
> 实测 `jzwid`=月亮岛立德楼时返回 22 间立德楼教室 + 1 间「月亮岛体育馆」。
> 因此教室清单和课表都要**在客户端再按教学楼名收窄一次**；
> 教学楼名带校区前缀时先剥掉前缀（`月亮岛立德楼` → `立德楼`）再比对，
> 收窄后为空则保留原始列表，避免"名字对不上 → 列表变空"。

> **连堂课的"看起来一样"未必是连堂**：只有**格子内容完全相同**才算连堂。
> 实测立德楼A401 的 0102 与 0304 都是「中外设计艺术史 凌翔」，但班级不同
> （视传2503H vs 视传2504H），是**两个平行班**同节上课，不能合并；
> 而立德楼A501 的两格班级完全相同，才是连堂。
> 合并依据必须是**整格文本**，不能只看课程名 + 教师。

### 1.7.1 教室课表的展示形态：矩阵，不是周视图

个人课表那种「星期 × 节次」的单课表网格**不能**用来查整栋楼：
同一节次里几十间教室都有课，堆在一个网格里会互相覆盖。
教务系统的「全校性教室课表」页用的是**矩阵**：

```
┌──────────┬───────────── 星期一 ─────────────┬───── 星期二 ─────┐
│ 教室     │ 0102 │ 0304 │ 0506 │ 0708 │ … │ 0102 │ 0304 │ …
├──────────┼──────┼──────┼──────┼──────┼───┼──────┼──────┼ …
│ 立德楼A401│中外设│中外设│自然地│自然地│   │      │      │ …
│ 立德楼A402│宏观经│统计学│概率论│      │   │ …    │      │ …
└──────────┴──────┴──────┴──────┴──────┴───┴──────┴──────┴ …
```

App 的教室模式因此单独渲染 `RoomMatrix`（`app/.../ui/timetable/RoomMatrix.kt`）：

* **行 = 教室**，按表格里的顺序；
* **列 = 星期 × 6 个节次对**，与表头一致（`0102`…`1112`）；
* 左侧教室名列**固定**，横向滚动时不跟着动；
* 连堂课只在起始格显示完整卡片，后续格标「连堂」；
* 点格子弹出课程详情（教师 / 班级 / 教室 / 上课时间 / 授课周次）。


### 1.8 场地选择的三级级联

教务系统把"在哪里上课"拆成三个下拉框，App 的选择界面与之一一对应：

```
校区（xqid）→ 教学楼（jzwid）→ 教室（classroomID）
```

* **校区**是服务端渲染的，直接从查询页的 `#xqid` 解析；
* **教学楼**由 `getJxlByAjax` 按校区加载；
* **教室**没有接口可用，从该教学楼的课表表格首列反推（见 1.5）。

因此选择是**级联**的：换校区要重拉教学楼，换教学楼要重拉教室。
`TimetableViewModel` 负责这条级联链，`RoomPickerDialog` 只负责展示与回调。

> **级联时的状态陷阱（已修）**：对话框里点选校区/教学楼会实时回调 ViewModel，
> 因此"确定"时不再与当前状态比较，而是与"屏幕上这份课表对应的查询条件"比较：
> 条件确实变了才重新请求，没变就不重复打慢页面。对话框点"取消"会回滚到打开前的选择。
